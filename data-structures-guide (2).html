Data structures,
explained like you've never seen one.

Every data structure is just an answer to one question: how should this data sit in memory so the operations I need are fast? Learn that reasoning, not the syntax, and you'll never forget which one to reach for.

the one idea underneath everything below

Imagine memory as a long street of numbered mailboxes. An array is renting a contiguous block of boxes and knowing the street numbers — so you can walk straight to box #47. A linked list is scattering boxes anywhere in the city, each one leaving a note with the next box's address — cheap to add a box anywhere, but you must follow the trail box-by-box to find #47. Almost every trade-off you'll read below is a variation of this one tension: contiguous and numbered (fast lookup, slow insert) versus scattered and linked (slow lookup, fast insert).

01

Array

A fixed row of memory slots, numbered from 0, where any slot can be reached instantly.

arr[2] doesn't search — it computes base_address + 2×slot_size and lands exactly there.

Think of it as a row of numbered parking spots. If you know a car is in spot 12, you drive straight there — you never scan spot 1, 2, 3... to find it.

Why it's fast

The address of any index is pure arithmetic — no searching. That's what makes lookup O(1).

Why it's rigid

The slots are contiguous, so the size is fixed at creation. Inserting in the middle means physically shifting every element after it.

OperationTimeWhy
Access by indexO(1)direct address math
Search (unsorted)O(n)must check each slot
Insert / delete at endO(1)no shifting needed
Insert / delete in middleO(n)everything after must shift
Use it when

You know the size upfront (or close to it), you need instant access by position, and changes mostly happen at the end. Pixel grids, lookup tables, fixed-size buffers, coordinates.

02

Dynamic array

An array that secretly outgrows itself — Python's list, Java's ArrayList, JS's Array.

This resize happens rarely — capacity doubles each time — so the average cost per append stays O(1).

The subtlety

Most appends are O(1). But whenever the backing array fills up, one append silently costs O(n) — it must allocate a bigger block and copy everything over. Averaged across many appends, this still works out to O(1) "amortized" — but if you're timing a single operation and it's mysteriously slow, this is why.

OperationTime
Access by indexO(1)
Append at endO(1) amortized
Insert / delete at front or middleO(n)
Use it when

This is your default "just give me a list" structure — reach for it first unless something specific (frequent front-insertion, key-based lookup) points elsewhere.

03

String

A read-only array of characters. Behaves like an array — with one dangerous exception.

The trap

Strings are immutable. Every "modification" — concatenation, slicing — actually builds a brand-new string in memory. Doing result += char inside a loop of n characters costs O(n) each time, O(n²) total. This is one of the most common silent performance bugs beginners write.

Slow — O(n²)
result = ""
for ch in text:
    result += ch  # new string each time
Fast — O(n)
parts = []
for ch in text:
    parts.append(ch)
result = "".join(parts)
Use it when

Representing text, obviously — but build long strings with a list + join, or a mutable buffer (StringBuilder in Java), never with repeated concatenation in a loop.

04

Linked list

Nodes scattered anywhere in memory, each one holding data plus a pointer to the next node.

Like a scavenger hunt: each clue (node) is hidden somewhere different, but tells you exactly where to find the next one. You can't jump straight to clue #5 — you must follow the trail from clue #1.

OperationTimeWhy
Insert / delete at a known nodeO(1)just rewire pointers, nothing shifts
Access by index / searchO(n)must walk node-by-node from the head
Also worth knowing

Because nodes live at scattered addresses, linked lists have worse CPU cache performance than arrays even when both are "O(n)" — in practice arrays are often faster for pure iteration.

Use it when

Frequent insertions/deletions, especially at the front, and you don't need index-based access. Building blocks for stacks, queues, and the classic LRU cache (paired with a hash map).

05

Stack — LIFO

Last in, first out. You only ever touch the top.

Pancake stack: you always eat (pop) the top one, and add (push) a new one on top.

Use it when

You see "undo," "matching/nesting," "next greater element," or you're doing DFS iteratively. Note: recursion itself uses a stack — that's literally what the "call stack" is, which is why deep recursion can overflow it.

Trigger phrase to watch for

Balanced parentheses / brackets, browser back-button history, expression evaluation — anywhere the most recent unresolved thing needs to be resolved first.

06

Queue & deque — FIFO

First in, first out. Add at the back, remove from the front. A deque does both ends.

Whoever joined the line first (A) leaves first — exactly like a queue at a checkout counter.

Why it matters

This ordering is exactly what BFS needs: to guarantee you find the shortest path, you must explore nodes in the order you discovered them — one queue does that automatically.

Use it when

"Process in arrival order," task scheduling, BFS / level-order traversal, sliding-window maximum (deque tracks candidates from both ends).

07

Hash map & hash set

The single most useful structure in interviews. Average O(1) lookup by key.

The instinct that should trigger this

The moment you catch yourself thinking "I'll loop through to find or count it" — stop. A hash map turns that O(n) scan into an O(1) lookup. This single realization solves a huge share of array and string interview problems.

OperationAverageWorst case
Insert / lookup / deleteO(1)O(n) — rare, adversarial collisions
Trade-off

No ordering is preserved (unless you use an ordered variant). If you need sorted iteration, a hash map alone won't give it to you.

Use it when

Counting, deduplication, "have I seen this," fast complement lookups (Two Sum), caching results you've already computed.

08

Heap / priority queue

Always hands you the smallest (or largest) item, without fully sorting everything else.

min-heap: every parent is ≤ its children, so the smallest value is always sitting at the root, ready in O(1).

Use it when

You only ever need "the current smallest/largest," not full sorted order — Dijkstra's algorithm, top-K elements, merging K sorted lists, running median (with two heaps).

OperationTime
Peek min/maxO(1)
Insert / removeO(log n)
Build heap from n itemsO(n)
09

Tree & binary search tree

Hierarchical nodes with children. A BST additionally keeps left < node < right.

To find 12: start at 8, go right (12>8), found it in 2 hops instead of scanning every node.

The catch

O(log n) only holds if the tree is balanced. Insert sorted data into a plain BST and it degenerates into a straight line — effectively a linked list, O(n). Self-balancing variants (AVL, Red-Black trees) guarantee balance automatically.

Use it when

Data is naturally hierarchical (file systems, org charts), or you need both fast search and sorted-order traversal at once — something arrays and hash maps can't both give you together.

10

Trie — prefix tree

A tree of characters, built so every path from the root spells out a stored word.

"cat" and "car" share the c→a path — the trie stores that shared prefix only once.

Why not just a hash set of words?

A hash set answers "is this exact word present" in O(1) — but can't efficiently answer "give me every word starting with 'ca'." A trie answers that in O(L), where L is just the prefix length, no matter how many thousand words are stored.

Use it when

Autocomplete, spell-check, IP routing tables — anywhere the trigger words are "starts with" or "prefix."

11

Graph

Nodes connected by edges — the only structure built for many-to-many relationships.

Unlike a tree, a node can connect back to any other node — cycles are allowed, hierarchy is not required.

Use it when

Anything with relationships between entities that aren't strictly hierarchical — maps, social networks, dependency graphs, circuit connections. Traverse it with BFS (shortest hops, unweighted) or DFS (explore everything, detect cycles).

12

Union-Find (disjoint set)

Tracks groups and merges them — answers "are these connected?" in near O(1).

Instead of re-running BFS/DFS every time a new edge arrives, union-find merges and checks groups near-instantly.

Use it when

Dynamic connectivity — edges are being added over time and you keep asking "are A and B connected now?" Also the standard tool for detecting cycles while building a graph edge-by-edge, and for Kruskal's minimum spanning tree.

13

The pairs that confuse everyone

Same-sounding, different guarantees. Read these once and the mix-ups stop.

Array vs dynamic array
Array
Fixed size, set at creation. Can't grow — you'd need to make a new one and copy everything.
Dynamic array
Same O(1) access, but grows itself by reallocating and doubling capacity when full. What Python list and Java ArrayList actually are.
Array vs linked list
Array
Contiguous memory → O(1) index access, but O(n) insert/delete in the middle (shifting).
Linked list
Scattered memory → O(n) to reach an index, but O(1) insert/delete once you're at the node.
Stack vs queue
Stack — LIFO
Last one in is the first one out. Pairs naturally with DFS and "undo."
Queue — FIFO
First one in is the first one out. Pairs naturally with BFS and "arrival order."
Hash map vs tree / BST
Hash map
O(1) average lookup, but no ordering — you can't cheaply ask "what's the next-smallest key."
BST
O(log n) lookup (slower), but keeps sorted order for free — range queries, "closest value," in-order traversal.
Heap vs BST
Heap
Only guarantees the root is the min/max. Great for "give me the extreme," useless for "give me everything in order" — that requires repeated removal.
BST
Guarantees full ordering (in-order traversal is sorted). Better when you need range queries or the k-th smallest at arbitrary times.
Trie vs hash map
Trie
Built for prefixes. "All words starting with 'pre'" is O(L), independent of dictionary size.
Hash map
Built for exact matches only. Answers "is this exact word present" in O(1), but prefix search means scanning every key.
Tree vs graph
Tree
A restricted graph: no cycles, exactly one path between any two nodes, strict parent/child hierarchy.
Graph
No restrictions — cycles allowed, a node can connect back to any other node, no required hierarchy.
BFS vs DFS
BFS — queue
Explores level by level. Use when you need the shortest path in an unweighted graph.
DFS — stack / recursion
Dives as deep as possible before backing up. Use for exploring all paths, connectivity, and cycle detection.

The part that actually matters in interviews

Which one do I use?

Six questions, asked in order, get you to the right structure almost every time.

1
Do I need order preserved by position (index)?
→ array or dynamic array
2
Do I need fast lookup by key, not position?
→ hash map / hash set
3
Is there a "most recent" or "first in" pattern?
→ stack (LIFO) or queue (FIFO)
4
Do I only care about the extreme (min/max), not full order?
→ heap / priority queue
5
Is the data naturally hierarchical or connected?
→ tree, trie, or graph — depending on shape
6
Am I merging or checking group membership as edges arrive?
→ Union-Find
